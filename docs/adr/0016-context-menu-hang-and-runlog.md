# ADR 0016 · 右键菜单卡死与「列表突然全空」

- 状态：已实施（v1.4.9）
- 起因：用户反馈「运行一会儿，右键什么菜单都不出来，最后刷新一下所有文件或文件夹
  都看不见了，又出现空白」，并要求加运行日志方便排查。
- 关联：[ADR 0009](0009-win11-tab-card-visual.md)（右键菜单「打开方式」入口）、
  [ADR 0011](0011-perf-batch-1.md)（文件夹大小协调者）、
  [ADR 0013](0013-async-directory-load.md)（目录异步读取）

## 现象与排查

日志（v1.4.9 新增的运行日志）在压力场景下一次就抓到了现场：

```
[perf ] 主线程卡顿 ≥ 500ms，正在 dump 卡住前最近 40 条事件：
[perf ]     │ 19:07:34.901 [menu ] 构建右键菜单 bug-a.png
[perf ]     │ 19:07:34.902 [menu ] 构建右键菜单 empty-dir.png
[perf ]     │ ... 同 4ms 内数百条 ...
[sys  ] fd=11 threads=10 rss=179MB menuBuilds=809
```

两个事实：

1. **SwiftUI 的 `.contextMenu { }` 是「预先求值」的** —— 不是右键时才构建，
   而是每一行的 body 求值时就把整套菜单构建出来。列表 200 行 = 一次渲染
   200 次菜单构建。
2. **任何 `@Published` 变化都会让整个列表重建**（`FileListView` 观察整个
   `BrowserModel`），于是「一次状态变化 = 全列表重建 = 行数 × 菜单构建」。

把这两条乘起来，就得到「运行一会儿就卡死」：只要有一个高频状态在动，
主线程每秒就要做几千次菜单构建。

## 三个叠加的高频源

| # | 源 | 原来 | 后果 |
|---|---|---|---|
| 1 | 「打开方式」候选 | 每行每次构建都同步查 LaunchServices（v1.4.4 引入，只按扩展名缓存，未命中就现查） | LS 数据库繁忙时阻塞数秒 → **菜单点了不出来** |
| 2 | 文件夹大小回填 | 每算完一个文件夹发一次 `@Published` | 200 个文件夹 = 200 次全量重建 |
| 3 | 传输进度 | 每 50ms 一次 | 10 次/秒 × 200 行 = 每秒 2000 次菜单构建 |

外加 `refreshFromDisk`（v1.4.7 遗留）仍在主线程同步读目录，与上面叠加。

## 决定

不重写菜单（改成 AppKit `NSMenu` 惰性构建的收益不足以抵掉重写风险），
而是**把菜单路径削到只剩内存操作 + 把高频发布合并**：

### 1. 菜单路径零 IO、零 IPC

- `openWithCandidates` / `defaultOpenWithApp`：**只读缓存**，未命中返回空并触发
  后台查询，查完写缓存并通知重绘。首次右键可能显示「正在读取候选应用…」。
- 预热：目录加载完成后，对可见项的**前 6 种类型**后台预取，正常使用几乎总能命中。
- `canPaste`：`pasteboard.changeCount` 是 XPC，改成**250ms 限速探测**，
  菜单里读缓存布尔值。
- `TerminalService.available`：进程内缓存（原来每次菜单构建 stat 三四个路径）。
- 解压目标文件夹名：菜单只显示纯字符串，不再 `stat` 避重名（点击时才计算）。

### 2. 合并高频发布

- `FolderSizeCoordinator`：结果攒 150ms 批量发布一次，替代逐项发布。
- 传输进度：50ms → 200ms。

### 3. 自动刷新移出主线程

`refreshFromDisk` 改为后台读 + 代次校验（与 `load` 同一套），并加
`isRefreshing` 防并发。vnode 事件仍在 watcher 层 0.25s 防抖。
自检用 `loadsDirectorySynchronously` 开关走同步路径，保持原有断言写法。

## 运行日志（同批交付）

偶发问题无法靠自检复现，所以补一套现场记录（`Services/RunLog.swift`）：

- 落盘：`~/Library/Logs/WinExplorer/WinExplorer-YYYY-MM-DD.log`，
  单文件 2MB 轮转、保留最近 5 个；
- 菜单栏「帮助 → 打开运行日志」直达，另有「记录一条现场标记」把当前
  目录/项数/选中数/加载态/fd/线程/内存钉进日志；
- **主线程卡顿检测**：后台每 100ms 投一次心跳，超过 500ms 就记一条，
  并 dump 卡住之前最近 40 条事件（能看出「卡在哪个动作之后」）；
- **资源采样**：每 30s 记 `fd / threads / rss / menuBuilds / 窗口内容尺寸`。
  `menuBuilds` 是「列表重算强度」，窗口尺寸用来区分「数据为空」和「视图零尺寸」；
- 默认开启（自检默认关闭，`WINEXPLORER_LOG=0` 也关）。`note()` 带 50ms 节流，
  避免「日志本身成为卡顿源」——这是写这套东西时立刻踩到的一个坑。

## 取舍

- **没有做真正的惰性菜单**：`contextMenu(forSelectionType:)` 或 AppKit `NSMenu`
  能做到「右键时才构建」，但要重写选择模型/全部菜单项，风险高于收益。
  当前把单次构建降到纯内存操作后，即使 200 行 × 每次渲染也在毫秒级。
- **持续写入时不刷新列表**：watcher 的 0.25s 防抖是「静默后才触发」，
  所以下载中的目录不会边下边刷新。这是原有行为，未改。
- **`windows=3`**：日志里窗口数包含菜单栏等辅助窗口，不必等于用户看到的窗口数。

## 验证

- 自检 zh / en 全 `SELFTEST OK`，新增 4 条：菜单首次只读缓存、后台查完后候选可用、
  缓存命中 500 次 < 100ms、资源采样能拿到 fd。
- 压力场景（280 项目录 + 连续写入）：主线程无卡顿记录，自动刷新 19ms。
- 实机运行 35s：`fd=11 threads=11 rss=234MB`，全程稳定无增长。
