# ADR 0010 · 「打开方式」：一次性打开与应用选择

- 状态：已实施（v1.4.4）
- 起因：用户要求给现有文件浏览加「打开方式」能力 —— 选择指定应用打开目标文件，
  并且要区分「这次用这个应用打开」和「以后都用这个应用打开」，同时处理
  应用不可用 / 权限不足 / 用户取消等情况。

## 决定

### 入口

右键菜单「打开」下面加 **「打开方式」子菜单**，结构：

```
打开方式 ▸
  TextEdit（默认）      ← 当前默认应用带「（默认）」后缀并排最前
  Visual Studio Code
  …
  ────────────
  其他…                 ← 系统选应用面板，一次性打开
  设为默认打开方式…      ← 系统选应用面板，改该类文件的默认应用
```

文件夹也有「打开方式」（用 VS Code 之类打开目录是常见需求），但没有
「设为默认打开方式」——macOS 的默认应用是按内容类型（UTI）绑定的，
文件夹类型统一由 Finder 处理，没有单目录的概念。

### 候选应用怎么来

`NSWorkspace.urlsForApplications(toOpen:)`（LaunchServices）查「系统认为能打开
这类文件的全部应用」，然后：

- 按 bundle id 去重（`/Applications` 与 `~/Applications` 常有两份副本）
- 按显示名 `localizedStandardCompare` 排序
- 默认应用提到最前
- 上限 8 个（再多就该走「其他…」了）
- 按**文件扩展名缓存**：右键菜单渲染时会问一次，这个查询是同步的，
  不缓存会拖慢菜单弹出；代价是应用刚被删掉时菜单里还留着它 —— 点的时候
  会再校验可用性并提示，可接受

### 一次性打开 vs 设为默认

两个动作完全分开，不共用一个确认框：

| 动作 | API | 副作用 |
|---|---|---|
| 一次性打开 | `NSWorkspace.open(urls, withApplicationAt:configuration:)` | 不改系统默认应用 |
| 设为默认 | `NSWorkspace.setDefaultApplication(at:toOpenFileAt:)` | 改 LaunchServices 的默认角色绑定 |

刻意不做「设为默认前弹确认」：系统设置里随时能改回来，多一层确认只是噪音。

### 异常处理

| 情况 | 处理 |
|---|---|
| 应用不可用（被移动/删除/不是 .app） | 打开前 `isAvailable` 预检 → 提示「找不到应用「X」，它可能已被移动或删除」 |
| 文件权限不足 | `blockedByUnauthorized` 走已有的**授权浮层**（不是干巴巴的错误条）；服务层再补一道 `isReadableFile` 预检，避免 LaunchServices 静默失败 |
| 用户取消选应用面板 | 直接 return，**不提示、不报错、无副作用**（取消是正常路径） |
| LaunchServices 返回错误 | 透传 `localizedDescription`，前缀「打开失败：」 |
| 多选 | 右键项在选中集合里就作用于整个选择，否则只作用于该项；候选类型取右键项 |

### 为什么不用 AppleScript

`tell application "X" to open ...` 会触发「想控制 X」的自动化授权弹框，而我们
只是要把文件 URL 递过去，不需要控制权。与 `TerminalService` 的取舍一致。

## 验证要点

自检（`WINEXPLORER_SELFTEST=1`，9 项新增断言，纯查询不改系统状态）：

1. 能为 .txt 列出候选应用且都指向 `.app`
2. 候选按 id 去重
3. 能查到默认应用
4. 不存在的应用被判定为不可用
5. 用不可用应用打开会得到 `.applicationUnavailable` 错误而不是静默失败
6. 错误文案里带应用名（可读）
7. 设为默认前也会先校验应用存在

手工验收（需要真人点菜单）：

- 一次性打开后，Finder 里双击同一文件仍是原默认应用（默认没被改）
- 「其他…」面板点取消 → 无提示、文件没被打开
- 「设为默认打开方式…」选完后，该扩展名的默认应用确实变了
- 把候选应用拖进废纸篓后再从菜单点它 → 提示「找不到应用…」
- 多选 3 个文件 → 打开方式 → 3 个都被同一应用打开
- 未授权的文件 → 弹的是授权浮层，不是错误条
