# ADR 0005 · 搜索框并入地址栏体系、编辑态的退出时机

- 状态：已实施（v1.3.1）
- 前置：`docs/adr/0001`（地址栏视觉向 Win11 对齐）
- 起因：用户截图指出两个问题 ——
  1. 地址栏编辑态（白底 + 蓝焦点环）旁边，搜索框还是**系统 bezel**（灰底渐变 +
     系统圆角），同高但底色 / 描边 / 圆角全都不一样，摆在一起像两个时代的控件；
  2. 地址栏处于编辑态、路径全选高亮时，**点击列表空白处或点击文件，
     编辑态和选中态都挂在原地不退**。

## 决定 1 · 搜索框完全并入地址栏容器体系

搜索框不再使用 `NSSearchField` 的系统 bezel（`isBezeled = false`、
`drawsBackground = false`、`focusRingType = .none`，并用空 cell 隐藏系统放大镜
与清除按钮），改由 SwiftUI 画与地址栏完全同一套容器：

| 属性 | 值（与 `PathBar` 地址栏一致） |
|---|---|
| 填充 | `controlBackgroundColor` 55% |
| 描边 | `primary` 9%，1pt |
| 圆角 | 6 |
| 高度 | 28 |
| 聚焦态 | `accentColor` 1.5pt 描边（即地址栏编辑态的焦点环） |

放大镜与清除按钮由 SwiftUI 绘制：放大镜常态 `secondary`、聚焦时变强调色；
搜索词非空时右缘出现 `xmark.circle.fill`，点击清空并保持焦点。
`NSSearchField` 本体保留（拿系统键盘行为、Esc 两次语义、⌘F 全选），
只是外观完全交给容器。

聚焦状态通过 `controlTextDidBeginEditing / controlTextDidEndEditing`
回调回 SwiftUI，驱动焦点环与图标颜色。

## 决定 2 · 编辑态在任何「用户转向列表」的操作时退出

地址栏编辑态的语义收紧为：**「用户正在输入路径」是一种独占的输入状态，
一旦用户把注意力转回列表，就必须退出**。新增的退出路径：

| 交互 | 行为 |
|---|---|
| 点击列表空白处 | 退出编辑态 + 取消文件选中（Windows：点空白 = 放下当前一切输入状态） |
| 单击文件行 | 退出编辑态；行的选中 / ⌘点行为不变 |
| 双击文件行 | 双击前必有单击，单击已退出 |
| ⌘F 聚焦搜索框 | 退出编辑态（两个输入状态互斥，后者胜） |

保留不变的退出路径：Esc、Enter 提交、导航、切目录、目录内容变化。

## 决定 3 · 搜索过滤是持续模式，不受点空白影响

搜索框里有过滤词时，点击列表空白**保留过滤结果** —— 只有 Esc（第一次清词、
第二次退出搜索）或清除按钮才退出。这与 Windows 一致：过滤是视图状态，
不是一次性输入；地址栏编辑态才是「正在打字」。

## 取舍

- 放弃系统搜索框外观换取与地址栏的一致性；键盘与 Esc 行为仍是系统的
- 不在右键菜单打开瞬间退出编辑态：SwiftUI 没有上下文菜单打开回调，
  而用户右键前几乎总有一次单击；为此加全局事件监听不值得
- 聚焦搜索框退出地址栏编辑，但反向不成立：进入地址栏编辑不清搜索词 ——
  用户可能改完路径还想继续过滤，替他清词是越权

## 验证

- SelfTest 新增断言：`handleClick` / `clearSelection` / `beginSearch`
  都会退出编辑态；原有 306 项零回归，zh / en 各一遍全 PASS
- 截图：地址栏编辑态 + 新搜索框同框（对比 1.3.0 的系统 bezel）、
  ⌘F 聚焦搜索框（焦点环 + 地址栏已退回面包屑）
- 右键菜单 / 真实键盘路径需用户手动确认
