# ADR 0008 · 标签栏左对齐、隐藏窗口标题与导航按钮

- 状态：已实施（v1.4.1）；布局细节修订于 v1.4.2
- 修订：[ADR 0006](0006-tab-bar-in-toolbar-and-file-transfer.md) 决定 1 的布局部分
- 起因：用户看 1.4.0 实机截图后反馈 —— 红框（标签 chips + `+`）「向左靠齐」；
  蓝框（← → ↑ 导航按钮 + 「WinExplorer」标题）「可以隐藏掉，多余了」。
  v1.4.2 追加反馈：红框（标签 chip）「字体调大一点」、蓝框（右侧视图按钮组）「右边对齐」。

## 决定

1. **标签栏从 `.principal`（居中）移到 `.navigation`（最左）**，成为工具栏
   第一个元素：`[标签A] [标签B] [+] ……（弹性空白）…… [视图 | 粘贴 | 新建 | 菜单]`。
   这是 Windows 11 资源管理器的真实形态（Win11 的标签也在左侧）。
2. **隐藏窗口标题**：`Window` 场景加 `.windowToolbarStyle(.unified(showsTitle: false))`。
   标题「WinExplorer」在工具栏里没有信息量（Dock、菜单栏、关于面板都有），去掉后
   工具栏左侧干净且给标签栏腾出空间；窗口标题本身保留，「窗口」菜单 / Command-Tab
   仍能按名找到窗口。
3. **移除 ← → ↑ 导航按钮**：用户明确要求连按钮一起隐藏。导航功能不删 ——
   「前往」菜单本就有 后退 ⌘[ / 前进 ⌘] / 上一级 ⌘↑（v0.x 起一直存在），
   且地址栏面包屑可点任意层级跳转。

## 为什么当初选 `.principal`、为什么错了

SwiftUI macOS 工具栏里只有 `.principal` 槽位是「居中且可撑开」的，于是 1.4.0
把标签栏放进去换来了「常驻 + 可拖放」；代价是被钉死在水平居中，左侧三个导航
按钮和窗口标题把它往右挤，视觉上「漂在中间」，和 Win11 的左对齐不符。
`.navigation` 槽位天然贴左，放进来后不需要 principal 的弹性 —— 标签超过
520pt 上限靠横向滚动（ADR 0006 取舍不变）。

## 取舍

- 鼠标用户从此没有「点按钮后退」，只能 ⌘[ / ⌘] / ⌘↑ 或点面包屑 —— 已被用户
  接受（这就是他点名要删的）
- 没有把导航按钮缩成菜单里的下拉塞回标签栏（Win11 也没有）—— 保持工具栏一行干净

## 验证

- SelfTest 全量 zh / en PASS（自检不断言工具栏按钮，纯模型层不受影响）
- 截图（`WINEXPLORER_SNAPSHOT_FULL=1`）：标签 chips + `+` 贴左，无标题无导航按钮

## v1.4.2 修订：字号与右对齐（同一个问题的下半场）

用户在这版截图里继续指出两处：标签 chip 字太小、右侧视图按钮组没有贴右。
第一条是纯调参，第二条挖出了一个 SwiftUI 的结构性问题。

**字号**：chip 标题 11.5 → 13pt，图标 13 → 15pt，`+`/关闭按钮同步放大 1pt，
chip 容器 32 → 34pt 高。之前 11.5pt 是跟着 macOS 侧边栏字号抄的，放在工具栏里
比右侧按钮的标签明显偏小，读起来「发虚」。

**右对齐为什么不能靠 `Spacer`**：实测（打印 `NSToolbarView` 里每个
`NSToolbarItemViewer` 的 frame）确认 —— SwiftUI 的工具栏 item **永远按内容的
理想尺寸布局**，宿主不会把剩余宽度提案给内容：

| 写法 | 实测结果 |
|---|---|
| `Spacer()` + `.frame(maxWidth: .infinity)` | item 仍按理想宽度，`Spacer` 塌成 0 |
| `.frame(width: 探针量到的窗口宽度)` | 背景铺满整宽，内容仍按理想宽左贴（`Spacer` 不展开） |
| `.primaryAction` 分组 | 本窗口里不会自动获得弹性空白，紧贴前一个 item |
| **`NSToolbar.insertItem(.flexibleSpace, at:)`** | ✅ 真正占住剩余宽度，把按钮组顶到最右 |

所以最终方案是 `ToolbarRightAlignFix`：挂在窗口背景上的一个零尺寸 NSView，
在窗口出现/尺寸变化/更新时，往 `NSToolbar` 的「标签栏之后、按钮组之前」插一个
`flexibleSpace`（幂等，重复插入会被去重）。SwiftUI 没有暴露这个标识，只能走
AppKit 这一层；这也是「标签栏用 `.fixedSize` 按内容收缩、右侧留白全部归弹性空白」
的前提 —— 否则 item 拿固定宽度会把 `+` 推离最后一个 chip。

**遗留**：`.fixedSize` 让标签条宽度随标签数增长，极端情况（10+ 标签）会挤压右侧
按钮组进「»」溢出菜单；日常 2–5 个标签无影响，若真遇到再引入「测量自然宽度 +
上限」的方案。

## 追加修订：弹性空白的自愈

用户反馈「右侧按钮组没有始终贴最右，换屏幕尺寸也会偏」。根因不在布局算法，
而在**弹性空白会被 SwiftUI 重建工具栏时冲掉**：标签增删、视图更新都会重设
item 列表，我们插进去的 `flexibleSpace` 随之消失，按钮组就回到紧贴标签栏的状态。

修法（`ToolbarRightAlignFix`）：
- 除窗口出现 / 尺寸变化 / 成为 key window 之外，**监听 `NSToolbar` 的
  `willAddItem` / `didRemoveItem` 通知** —— SwiftUI 重建 item 时必然触发；
- 触发后合并到下一轮 runloop 再检查（幂等：有弹性空白就什么都不做），
  避免在 AppKit 更新流程里反复改工具栏；
- 插入后额外在 +0.2s / +0.8s 各校验一次，被冲掉立刻补回。

实测（加两个标签，正是之前会把弹性空白冲掉的场景）：
`179+307 | 486+658(弹性空白) | 1144+124 | 1268+39 | 1307+41 | 1348+59`，
窗口 1415 → 按钮组右边缘 1407，距右 8pt。窗口缩放时弹性空白自动伸缩，
不需要重新插入。
